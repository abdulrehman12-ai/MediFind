# Phase 2 pharmacy catalog

Phase 2 adds pharmacy profiles, staff memberships, a medicine catalog, and pharmacy inventory behind two Filament panels. It does not add customer search, maps, prescriptions, orders, checkout, payments, notifications, or a mobile client. Cash on Pickup remains the only intended MVP payment method, and this phase does not create an order.

The `medifind-app:phase1a-localdev` and `medifind-nginx:phase1a-localdev` images stay local-development images. Publishing Filament assets into those images does not make them production-ready.

## Accounts

Customers continue to sign in with mobile OTP. Pharmacy staff and administrators use a separate account: an email address, a password the invited person sets, and a required authenticator-app code. A customer email cannot be converted into a staff or admin account. Staff phone numbers stay empty so the customer phone uniqueness rule is unchanged.

The first administrator is created with `php artisan medifind:provision-admin {email}`. The command prints a single-use accept link once. Administrators invite the first pharmacy manager and may invite or assign a pharmacist. A new pharmacist membership starts unverified. Managers invite inventory staff only while the pharmacy is pending or approved. A manager cannot invite another manager, a pharmacist, or an administrator, and cannot mark a pharmacist credential as verified.

Invitation tokens are 32 random bytes. The database stores an HMAC-SHA256 hash of the token keyed with `APP_KEY`. Until Mailpit, or a future mailer, accepts the message, a separate outbox row holds the same token encrypted with `APP_KEY`. That ciphertext is deleted when delivery is recorded, and also when the invitation is accepted, revoked, superseded, or expires before a send. The raw token is not written to audit metadata or application logs. The accept link puts it in the query string of `/invitations/accept` so Nginx access logs, which record `$uri` without the query string, do not keep it. The token expires after 24 hours and is single-use.

Email and PostgreSQL do not commit together. Creating or reissuing an invitation inserts the invitation and one encrypted outbox row in the same database transaction. After that transaction returns, mail is sent only when the connection transaction level is zero. If an outer transaction is still open, an after-commit callback applies the same rule and still does not send while a transaction remains open. A savepoint release, a rolled-back transaction, and Laravel's test transaction (which stays open at level 1) do not send mail and do not mark the invitation delivered. Acceptance stays disabled while `delivery_status` is `pending`. Claiming, reissuing, revoking, accepting, expiring, releasing a failed claim, and recording delivery all lock the invitation row and then its outbox row. Those locks are released before the mailer is called. Each claim stores a new claim id. Only the sender that still finds that id can mark delivery or clear the claim. A sender that finishes after a newer claim or replacement does not delete that row or mark its token delivered. Reissue is rejected while a claim is inside its 30-second lease; the message tells the caller to try again, and the outbox row is left unchanged. After the lease, `php artisan medifind:deliver-invitations` can claim the row again. A send failure leaves a pending or already delivered invitation as it was, clears only the matching claim, and records `invitation_delivery_failed` without the token, the address, or the mailer message. Delivery is at least once: a crash after the mailer accepts the message and before the delivered mark can send the same message again on retry. The ciphertext is removed when delivery is recorded, and also when the invitation is accepted, revoked, superseded, or expired before a send. Only a delivered invitation whose token has not expired has a usable link. Reissuing that invitation keeps the link until the replacement message is accepted and the hash swap commits. If the replacement send fails, the previous link still works until its own expiry. Reissuing a pending invitation, including one whose earlier send failed, replaces the unpublished token immediately. Neither token can be accepted until a later send is marked delivered, and the failure message does not say that a previous link works. An invitation that is revoked or accepted while a send is in flight does not become usable when that sender finishes. A stale send, or a send that already passed the pre-send check before revocation or acceptance, can still produce an email, and the link in that email cannot be accepted. Mailpit at `127.0.0.1:8025` is only for local inspection. This phase does not configure a live email provider.

There is no self-service password reset after acceptance. A first-time invitee sets a password. An existing staff or administrator account must sign in and confirm the invitation; a password submitted on that path is rejected and is not stored. The invited person is the only one who chooses a new password.

## Pharmacy state

A pharmacy is `pending`, `approved`, `rejected`, or `suspended`. Public eligibility is not a browser field. It is true only when status is approved, the license review is verified, and the location review is approved. Rejected pharmacies can still sign in, correct the profile, and submit an appeal that returns the pharmacy to pending. They cannot approve themselves. Suspended pharmacies can still sign in so the status page is visible, but staff inventory edits, operating-hours replacement, and manager-issued invitations are denied until an administrator reinstates the pharmacy. Those staff writes lock the pharmacy row, then the actor and the active membership, and they recheck the pharmacy status, the actor's account status, and the membership inside that transaction. An administrator can still change inventory, replace hours, and invite staff for a suspended pharmacy; the staff checks are not applied to an administrator. A staff write that is still waiting when suspension commits does not change inventory, hours, or invitations and does not write an audit event. A suspension that is waiting on an in-flight staff write applies only after that write commits, and it leaves the committed write in place. Suspension and reinstatement increment `users.session_generation` for members so older panel sessions stop working.

Operating hours use Asia/Karachi wall-clock times. A closed day has no rows. A 24-hour day is an `all_day` interval. Split shifts are multiple `same_day` intervals. An `overnight` interval continues onto the next weekday, and Sunday wraps to Monday. Equal clock times are invalid. Overlaps are rejected in application code and by a database trigger. The trigger and the hours writer lock the pharmacy row so two replacements cannot commit an overlapping merged set. Adjacent intervals that meet at the same minute do not overlap.

## Verification records

License, location, and pharmacist credential reviews store the reviewing administrator, the review time, the method `documented_admin_review`, and evidence notes. A status flag or a typed license number is not verification. Database checks require those fields to be present, not merely unknown, before a verified or approved state is stored. Changing the license number clears license verification, including a direct database update. Changing coordinates clears location approval the same way. Review updates lock the pharmacy row and refuse to apply a review when the license number or coordinates no longer match the values being reviewed. `credential_status` is separate from `staff_role`. Only an active administrator can verify an active pharmacist who has a nonblank license number. Changing the role or the license number clears that verification. These rows are an operational record of an administrator's review. The software does not establish legal or Pakistani licensing compliance.

## Catalog and inventory

A medicine can be saved inactive without a manufacturer. Activating it, or adding it to inventory, requires a generic name, strength, dosage form, and manufacturer. Distinct strengths, dosage forms, and manufacturers stay distinct. An alias is unique only for one medicine and may point at several medicines.

General-use text is stored as `draft` with a source citation. The database rejects every other review status. There is no approval transition and no customer-facing publication.

Inventory quantity and cash price use integers. Price is stored in paisa and must be zero or greater. `last_verified_at` is set by the server in UTC when the stock status is not `unknown`. Phase 2 does not apply a customer freshness window. Controlled medicines may have an internal inventory row, and pickup stays off. Turning an existing medicine into a controlled medicine, or changing it from active to inactive, clears pickup on its inventory rows and increments the version of each row that was pickup-eligible. Reactivation does not turn pickup back on. A deferred constraint rejects any inventory row that is still pickup-eligible for an inactive or controlled medicine. The inventory guard still rejects a new pickup flag, a new inventory row, and other edits while the medicine is inactive; the only inventory update it allows in that state is the cleanup that turns pickup off. There is no control that turns pickup on for a controlled medicine. Updates send the current `version`; a stale version fails and leaves the row unchanged. Sensitive state changes and their audit rows commit or roll back together. Expected inventory, hours, and pharmacy-rule failures are shown in the panel as form notifications.

## Panels

`/admin` is only for active administrators. `/pharmacy` is only for active pharmacy staff, and each request is limited to pharmacies where that person has an active membership. Customers cannot open either panel. Inventory queries are limited to the current pharmacy, and delete actions are disabled. Authenticator secrets and recovery codes are encrypted and hidden from serialization.
